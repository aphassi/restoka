# LLM-оркестратор Restoka

`llm/` содержит обработку событий с помощью языковой модели. Оркестратор получает `request` и `context` от существующего `ScenarioRunner`, загружает актуальное состояние и историю диалога, вызывает модель и выполняет разрешённые действия через `context.tools.call()`.

Цикл оркестрации выполняет LangGraph `StateGraph`. Узлы `ask_model`,
`execute_tools` и `finalize` передают управление по результату текущего шага.
Один запуск графа обрабатывает одно входное событие. История, состояние заказа
и идемпотентность хранятся в PostgreSQL через действующие интерфейсы Restoka.

## Состав

| Файл | Назначение |
|---|---|
| `llm/runner.py` | Цикл обращений к модели, вызовы инструментов, обработка сбоев и формирование `RunResult` |
| `llm/prompts.py` | Общие инструкции и выбор блоков по типу события и входным данным |
| `llm/context.py` | Подготовка события, снимка состояния и истории для запроса к модели |
| `llm/verification.py` | Сверка фактов и заявлений о выполненных действиях с состоянием и ответами инструментов |
| `llm/clients.py` | HTTP-подключение к Chat Completions API; по умолчанию используется адрес DigitalOcean |
| `llm/tool_descriptions.py` | Описания инструментов и передача их JSON Schema модели |
| `llm/__init__.py` | Экспорт классов пакета `llm` |
| `tests/test_llm_runner.py` | Тесты с подставными ответами модели, без сети и PostgreSQL |
| `evaluation/run_llm_visible_one.py` | Запуск одного сценария из visible-набора через общий `ScenarioRunner` |

`run_llm_visible_one.py` нужен для **ручной проверки интеграции**: он выбирает один тест, запускает оркестратор и сохраняет результат и трассировку. Он не используется при обычной работе приложения, не создаёт набор тестов и не рассчитывает итоговые метрики.

## Как работает оркестратор

1. Получает новое событие (`request`) и параметры выполнения (`context`).
2. Запрашивает актуальные данные через `context.state.load()` и историю диалога через `context.history.recent()`, если она доступна.
3. Передаёт модели инструкции Restoka, нужные бизнес-данные, историю, текущее событие и описания доступных инструментов.
4. Если модель вернула `tool_calls`, проверяет и выполняет их через `ToolGateway` и снова обращается к модели с результатами.
5. Проверяет итоговый JSON и опасные заявления о выполненных действиях, возвращает `RunResult` и сохраняет историю.

В пользовательском диалоге модель интерпретирует запрос и выбирает инструменты.
Для первой отправки нужен `submission_id`, полученный от `create_order` в текущем
событии, либо сохранённое согласование на связанный заказ в событии решения
управляющего. Уже начатая отправка сверяется по своему сохранённому идентификатору.

Изменение предложения поставщика не считается подтверждённым изменением уже оформленного заказа. После неопределённого результата внешней отправки оркестратор не выполняет повторную отправку автоматически.

Для вычислений оркестратор сверяет итоговые числа с результатами инструментов. Для нескольких эквивалентных названий расчётных полей (например, `shortage_quantity` и `deficit`) предусмотрено сопоставление. При отказе итоговый результат содержит `metadata.verification_reason` и, если применимо, `metadata.unverified_fact_fields` — названия неподтверждённых полей без их значений. Проверки не гарантируют достоверность всего свободного текста; особенно важные действия с заказами проверяются отдельно.

## Инструкции модели

`build_system_prompt()` добавляет к общим правилам Restoka инструкции для
текущего события. Общие правила определяют источники данных, запреты и формат
`FinalDecision`. Блоки расчёта потребности и отправки переиспользуются там,
где эти действия нужны.

| Вход | Инструкции |
|---|---|
| `user_message` | Различение справочного запроса и покупки, уточнения, сравнение, согласование и статус заказа. Для переданного `proposed_order` добавляются правила проверки его условий и идентификаторов. |
| `time_tick`, `scheduled_review` | Отчётная дата, журнал активности и статус доставки. Для `scheduled_review` код формирует тело из журнала с совпадающими датой и дайджестом. |
| `scheduled_wakeup` | Самостоятельная проверка рисков и закупка в пределах политики. |
| `supplier_reply` | Проверенный ответ поставщика, обновление условий и оценка частичного подтверждения. |
| Уведомление, цитата поставщика или таблица | Применяются отдельные инструкции по оценке уведомления, извлечению условий из цитаты или сравнению предложений. |
| `manager_decision`, `external_result` | Продолжение согласованного заказа или сверка известной внешней операции. |

Оркестратор выбирает маршрут по типу события и уже распознанным структурированным
данным. Интерпретация пользовательского текста и выбор инструментов остаются
за моделью, а допуск вызова, бизнес-ограничения и проверка ответа — за Python.

## Проверка без API-ключа

В корне проекта `kt3`:

```bash
python -m pip install pytest
python -m pytest -q tests/test_llm_runner.py
```

Эти тесты не требуют Docker и не отправляют запросы в DigitalOcean.

## Запуск одного сценария

После настройки PostgreSQL по `SETUP.md` и получения API-ключа:

На macOS (в том же терминале, где настроена база):

```bash
read -rs "RESTOKA_LLM_API_KEY?Ключ DigitalOcean: "
echo
export RESTOKA_LLM_API_KEY
export RESTOKA_LLM_MODEL="deepseek-v4.1-flash-1017"
export RESTOKA_LLM_ENDPOINT="https://inference.do-ai.run/v1/chat/completions"
python -m evaluation.run_llm_visible_one --id R-001 --dataset eval_visible.json
```

Внешние операции поставщиков в тестовом `ScenarioRunner` имитируются. Обращения к модели через API оплачиваются по тарифу провайдера.

Настройки: `RESTOKA_MAX_COMPLETION_TOKENS` (по умолчанию 1024), `RESTOKA_LLM_TIMEOUT_SECONDS` (30 секунд), `RESTOKA_LLM_STREAM` (`1` для потокового ответа и измерения TTFT). Для расчёта стоимости по фактическим токенам можно указать `--input-price-per-million` и `--output-price-per-million`.

`max_rounds=12` — настраиваемый предел вызовов модели на одно событие, а не количество, которое обязательно будет выполнено. Размер входа дополнительно ограничен 60 000 символами; это не точный токеновый бюджет. Тарифы не вшиты в код: без них стоимость остаётся неизвестной.

Результаты сохраняются в `harness_runs_llm/<run_id>/`. Файл `evaluator.json` может содержать текст сообщений; не публикуйте его вместе с ключами или конфиденциальными данными.

## Проверка на реальной модели

На одной версии оркестратора с реальным DeepSeek прошли 128 из 128 видимых сценариев. Результаты и настройки сохранены в [отчёте КТ3](../reports/kt3/llm_visible_128/summary.json). Команды для полного прогона приведены в [SETUP.md](../SETUP.md#прогон-deepseek).

## Плановое пробуждение

Событие `scheduled_wakeup` сообщает, что пора проверить текущее состояние.
Продьюсер может записать произвольную метку в `reason`. Расписание,
остатки, заказы и предложения агент читает
через инструменты. Инструкции пробуждения берутся из системного промпта
оркестратора. Политика организации и повторная проверка потребности в
инструментах ограничивают автоматическую закупку.

Двухшаговый MS‑V‑008 входит в текущий видимый набор. Проверка с ответами модели из теста проходит локально через PostgreSQL. Для запуска с реальной моделью используйте ID сценария.

```bash
python -m evaluation.run_llm_visible_one --id MS-V-008 --dataset eval_visible.json
```
