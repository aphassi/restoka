# ADR-001: Выбор гибридной архитектуры LLM-агента для Restoka

**Статус:** Accepted\
**Дата:** 23.11.2026\
**Проект:** Restoka\
**Решение:** Гибридная архитектура: LLM-оркестратор + детерминированные инструменты и проверки.

## 1. Контекст

Restoka автоматизирует планирование и сопровождение закупок расходных материалов для сервисных организаций.

Система должна обрабатывать пользовательские запросы, изменения расписания и остатков, а также сообщения поставщиков. При этом закупочный процесс может быть многошаговым: поставщик меняет условия доставки, часть товара оказывается недоступна, требуется уточнение или согласование управляющего.

Основная архитектурная сложность заключается в необходимости одновременно обеспечить гибкость обработки неструктурированной информации и надёжность финансово значимых операций.

LLM хорошо подходит для интерпретации естественного языка и выбора дальнейших действий в нестандартных ситуациях, но не гарантирует соблюдение бюджетных ограничений, отсутствие дублирующих заказов и корректность численных расчётов.

Поэтому необходимо определить, какую часть управления закупочным процессом передать LLM, а какую оставить программным компонентам.

## 2. Рассмотренные альтернативы

### Вариант A. Полностью детерминированный pipeline

Вся логика закупок реализуется последовательностью заранее определённых правил и переходов.

**Преимущества:**
- Предсказуемое выполнение операций.
- Простота тестирования и воспроизводимость результатов.
- Отсутствие затрат на LLM API.

**Недостатки:**
- Сложность обработки свободных сообщений поставщиков.
- Необходимость вручную описывать большое число нестандартных сценариев.
- Ограниченная гибкость при изменении условий закупки.

Этот вариант выбран в качестве baseline для оценки дополнительной пользы LLM.

Его можно выбрать для основной системы, если поставщики и пользователи передают условия в структурированном виде и правила покрывают изменения процесса. Тогда преимущества свободной интерпретации не оправдают расходы на модель и дополнительные проверки.

### Вариант B. Полностью агентная архитектура

LLM самостоятельно планирует процесс, выбирает действия, выполняет расчёты и принимает решения об оформлении заказов.

**Преимущества:**
- Гибкое управление многошаговыми сценариями.
- Возможность адаптироваться к новым формулировкам и условиям.
- Меньшая зависимость от заранее заданных сценариев.

**Недостатки:**
- Риск неверных расчётов и некорректного выбора инструментов.
- Возможность нарушения бюджетных ограничений.
- Сложность воспроизводимости и проверки решений.
- Зависимость качества и задержки от поведения модели.

Для Restoka такой уровень автономности неприемлем из-за риска финансовых ошибок.

Этот вариант можно было бы рассмотреть для прототипа, который формирует только рекомендации, если ошибки легко исправить и каждое внешнее действие всё равно выполняет человек.

### Вариант C. Гибридная архитектура

LLM управляет последовательностью действий, интерпретирует неструктурированные данные и формирует объяснения. Детерминированные компоненты выполняют расчёты, проверяют ограничения и контролируют изменение состояния системы.

**Преимущества:**
- Гибкость при обработке нестандартных ситуаций.
- Программное обеспечение критических бизнес-ограничений.
- Возможность тестировать инструменты независимо от LLM.
- Сохранение состояния процесса и проверяемости действий.

**Недостатки:**
- Более сложная интеграция компонентов.
- Необходимость поддерживать схемы инструментов и их валидацию.
- Дополнительные затраты на трассировку, обработку ошибок и восстановление состояния.

## 3. Принятое решение

**Выбираем вариант C: гибридную архитектуру с LLM-оркестратором и детерминированными инструментами.**

Разделение ответственности следующее:

| Компонент | Ответственность |
|---|---|
| LLM-оркестратор | Интерпретация запросов, выбор следующего инструмента, обработка ответов поставщиков, уточнения, объяснения |
| Детерминированные инструменты | Расчёт потребности, проверка складских остатков, сравнение предложений, формирование заказов |
| ToolGateway | Проверка допустимости вызовов, параметров и прав доступа |
| Бизнес-правила | Бюджетные ограничения, необходимость согласования, предотвращение дублирования |
| PostgreSQL | Хранение состояния закупок, событий, заказов и истории действий |
| Harness и evaluator | Воспроизводимый запуск сценариев и независимая проверка результатов |

Оркестратор может выбирать допустимые следующие действия, но не может обходить проверки инструментов.

Перед оформлением заказа детерминированный код проверяет обязательные условия. Если данных недостаточно, превышен лимит или требуется согласование, автоматическое оформление блокируется.

Оплата заказов находится вне функциональности Restoka.

Для многошаговых процессов предусматриваются сохранение состояния, ограничение числа вызовов модели, обработка ошибок инструментов и возможность восстановления выполнения.

В КТ3 LangGraph управляет обращением к модели, выполнением инструментов и проверкой финала. Состояние закупки сохраняется в PostgreSQL и доступно на следующем событии. Плановое пробуждение может начать проверку потребности без запроса пользователя. Условия автоматической закупки проверяются инструментами и политикой организации.

## 4. Последствия решения

**Положительные:**

- LLM используется там, где необходима работа с естественным языком и неопределённостью.
- Критические ограничения обеспечиваются кодом, а не только инструкциями модели.
- Детерминированный baseline позволяет оценивать дополнительный вклад агентной архитектуры.
- Результаты можно проверять по трассировкам, событиям и состоянию PostgreSQL.

**Отрицательные:**

- Увеличивается сложность разработки и сопровождения.
- Требуется синхронизация схем инструментов, состояния процессов и документации.
- Ошибки интерпретации LLM сохраняются как отдельный источник риска.
- Дополнительные вызовы модели могут увеличивать задержку и стоимость.

**Принятый компромисс:** качество и безопасность закупочных решений имеют приоритет над максимальной автономностью и минимальной задержкой. Если система не может подтвердить корректность действия, она должна запросить уточнение или передать решение человеку.

## 5. Как проверяем решение

Для проверки архитектуры используем общий eval-набор для детерминированного baseline и LLM-агента.

Сравниваем:
- корректность выбранных действий и итогового состояния системы;
- соблюдение критических бизнес-ограничений;
- обработку многошаговых сценариев и неопределённости;
- корректность работы инструментов и восстановление после ошибок;
- задержку, число LLM-вызовов и стоимость обработки.

Baseline проверен на 130 видимых сценариях версии `restoka-eval-v1.4`. Оценщик проверяет действия, факты, состояние PostgreSQL и трассировки. Бюджеты, согласования и ежедневные ревью дополнительно проверяются отдельными аудитами.

Полный прогон DeepSeek на предыдущем наборе дал 128 из 128. Два добавленных сценария проверили отдельно. MS‑V‑009 прошёл 42 из 42 проверок с DeepSeek, MS‑V‑010 прошёл 11 из 11 проверок лимита шагов без вызова модели. Для прямого сравнения с baseline обе конфигурации нужно оценивать на одном наборе и одной версией оценщика.

Результаты baseline являются контрольной точкой для дальнейшего сравнения с LLM-архитектурой. Само наличие LLM не считается доказательством улучшения: агентный вариант должен показать дополнительную пользу без нарушения критических ограничений.
